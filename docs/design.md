# Design: an LLM that builds Mileti-style deductions, constrained by PDDL, informed by a knowledge graph, checked by Lean

*2026-11-12. Main grad-school project. Covers Mileti, A Mathematical Introduction to Mathematical Logic (2020), Chapters 1–3.*

## 1. Intent

Small and large LLMs make mistakes in formal proofs that you can check. This project asks whether two kinds of structure make them more reliable at building **formal deductions in propositional logic**:

- **Knowing which moves are legal** (PDDL)
- **Knowing what the book says** (a knowledge graph)

A Lean "gate" checks every step.

It is the next step after the calculus procedural knowledge-graph study, with two changes: SymPy grading becomes Lean checking, and calculus becomes logic. It is also how the author learns the material. **The author writes the syntax, the proof rules and how they combine in Lean, by hand.**

## 2. Goals, non-goals, anti-goals

**Goals**
- Lean code, written by the author, for Mileti's propositional syntax (Ch. 2–3.1) and the 14 deduction rules of §3.4. The code accepts a valid deduction and rejects an invalid step.
- A PDDL domain that mirrors those 14 rules. At any proof state, it determines which rules are legal.
- A knowledge graph of the book's content for Ch. 1–3: definitions, rules, worked examples, strategies and pitfalls.
- An LLM loop where the LLM picks one legal rule at each step and Lean checks it.
- An experiment with a measurable result (§7). Target: a workshop paper and arXiv preprint, Summer 2027.

**Non-goals**
- Chapter 4 and later (first-order logic). Possible phase 2 after the paper.
- Proving metatheorems such as soundness, completeness and unique readability with the LLM. The author may prove soundness in Lean by hand as a learning exercise; that is separate from the benchmark.
- Using Mathlib's logic library. The system must match Mileti's definitions exactly.

**Anti-goals (failure even if it runs)**
- The LLM or Claude writes the author's Lean rules. That defeats the learning goal and the claim in the application.
- A demo with no comparison against baselines.
- Copying book text into the public repo. Paraphrase and cite; the PDF stays out of git.

## 3. Mileti's proof system (paraphrased from §3.4; this is the spec)

A **line** is a pair `S ⊢ φ`: a finite sequence of formulas `S` (order and repeats matter) and one formula `φ`. A **deduction** is a sequence of lines. Each line is either an `Assume` line or follows from earlier lines by one rule.

| Rule | From | Conclude | Side condition |
|---|---|---|---|
| Assume | — | `S ⊢ φ` | φ occurs in S |
| ∧EL | `S ⊢ φ∧ψ` | `S ⊢ φ` | |
| ∧ER | `S ⊢ φ∧ψ` | `S ⊢ ψ` | |
| ∧I | `S ⊢ φ`, `S ⊢ ψ` | `S ⊢ φ∧ψ` | same S in both |
| ∨IL | `S ⊢ φ` | `S ⊢ φ∨ψ` | ψ is **any** formula (must be supplied) |
| ∨IR | `S ⊢ ψ` | `S ⊢ φ∨ψ` | φ is any formula |
| →E | `S ⊢ φ→ψ` | `S,φ ⊢ ψ` | |
| →I | `S,φ ⊢ ψ` | `S ⊢ φ→ψ` | φ is the **last** assumption |
| ∨PC | `S,φ ⊢ θ`, `S,ψ ⊢ θ` | `S,φ∨ψ ⊢ θ` | same S, same θ |
| ¬PC | `S,ψ ⊢ φ`, `S,¬ψ ⊢ φ` | `S ⊢ φ` | same S, same φ |
| Contr | `S,¬φ ⊢ ψ`, `S,¬φ ⊢ ¬ψ` | `S ⊢ φ` | same S, φ, ψ |
| Expand | `S ⊢ φ` | `S,γ ⊢ φ` | γ any formula |
| Delete | `S,γ,γ ⊢ φ` | `S,γ ⊢ φ` | |
| Reorder | `S₁,γ₁,γ₂,S₂ ⊢ φ` | `S₁,γ₂,γ₁,S₂ ⊢ φ` | swap two adjacent assumptions |

Formulas are built over atoms with ¬, ∧, ∨, →. Mileti writes them in Polish (prefix) notation as strings, generated by a free generating system (Ch. 2). Representing them as an inductive type in Lean is fine. Proving that the type matches the string version (unique readability) is optional learning work.

## 4. Architecture

```
            ┌──────────── knowledge graph (book meaning) ──────────┐
            │  definitions, rules, worked examples, strategies,    │
            │  pitfalls, depends_on edges                          │
            └───────────────▲──────────────────────────────────────┘
                            │ query (tool call)
goal S⊢φ ──► PDDL state ──► LLM picks one legal rule + arguments ──► Lean gate
                ▲   legal moves                                         │
                └──────────── accept: new state  /  reject: error ◄─────┘
```

1. **Goal.** A sequent `S ⊢ φ`.
2. **PDDL.** Holds the proof state and lists the legal rule applications.
3. **Knowledge graph.** The LLM may query it about definitions, rules, strategies and similar worked examples.
4. **LLM.** Picks exactly one rule and supplies its arguments: which lines, and any free formula for ∨I, Expand or Contr.
5. **Lean gate.** Checks the step with the author's rules. If Lean rejects it, the error goes back to the LLM. Repeat until the goal is proved or the step budget runs out.

### 4.1 Proof direction (builder's call; recommendation)
Work **backward (goal-directed)**. The state is a set of open goal sequents. A rule turns one open goal into 0, 1 or 2 new open goals; Assume closes a goal. This matches how people search, and every rule has a clear "conclusion shape" precondition. PDDL then encodes rules as actions that delete an open goal and add its premises.

### 4.2 Keeping PDDL finite
Working backward, most rules' premises are fixed by the goal: ∧I, ∨IL, ∨IR, →E, →I, ∨PC, Expand, Delete and Reorder. Four rules need a formula the goal doesn't contain: ∧EL and ∧ER need the other conjunct, ¬PC needs the case formula ψ, and Contr needs the contradiction formula ψ. So PDDL can't list every move. Ground every formula argument over a **finite candidate set**: the subformulas of the goal and assumptions, closed under one negation. The LLM may propose a formula outside that set. The PDDL check then says "unknown", not "illegal", and Lean decides. Log how often that happens.

### 4.3 The Lean gate interface (spec only; the author writes the Lean)
- **Input:** a deduction as numbered lines, each line `(S, φ, rule, premise line numbers, extra formula args)`. Python writes it to `lean/Generated/Attempt.lean` as a term built from the author's definitions.
- **Check:** `lake env lean lean/Generated/Attempt.lean`. Exit code 0 means valid; otherwise Lean's error message names the failed step.
- **Recommended Lean shape (author's choice):** an inductive `Formula`; a `Line` structure; a checker `checkStep : List Line → Step → Option Line`. Either prove `decide`-style soundness of the checker, or define an inductive `Derivable : List Formula → Formula → Prop` with one constructor per rule. The `Derivable` version is closer to Mileti's generating-system definition, and is the better learning exercise.
- Per step, the gate returns: accepted (the new line), or rejected (which side condition failed).

## 5. Knowledge graph (the "semantics": what the book means)

**Decision (author, 2026-11-25):** the graph is **LLM-extracted only** (`kg/extracted/`, built with the competition's extraction pipeline). The author writes the Lean rules and the gates, nothing else. There is no hand-written graph and no condition C. The node types below describe the extracted graph.

Node types:

| Type | Example |
|---|---|
| `definition` | formula, line, deduction, consistent, `S ⊨ φ` |
| `rule` | one per row of §3 |
| `example` | each worked deduction in §3.4 |
| `strategy` | "to prove φ→ψ, use →I and assume φ"; "to use a disjunction in the assumptions, use ∨PC"; "when stuck, use Contr on ¬φ" |
| `pitfall` | "∧I needs identical assumption sequences"; "→I only removes the *last* assumption, so Reorder first" |
| `theorem` | Prop. 3.4.9 (permutations), 3.4.10 (an inconsistent set proves everything) |

Edges: `depends_on`, `uses_rule`, `illustrates`, `pitfall_of`, `strategy_for`.

Format: `kg/nodes.jsonl` and `kg/edges.jsonl`, one JSON object per line. Text is in the author's own words, with a book section reference.

## 6. Benchmark

The book has only about 9 object-level deductions in Ch. 2–3. These are the 6 deductions in §3.4 (5 written out, 1 stated) and exercises 3.7 #7, #8a and #8b, listed in `benchmark/book_items.jsonl`. Everything else in §2.6 and §3.7 is metatheory or semantics, which is out of scope. So:

- **Book set (about 9):** a development and sanity set, not the main result.
- **Generated set (main, about 100–200):** random valid sequents over 2–4 atoms, filtered by a truth-table check (sound and complete for the §3.4 rules, per §3.5). Sort them by difficulty using the shortest proof found by a simple breadth-first prover. Fresh sequents avoid training-data contamination.

## 7. Experiment

| Condition | What the LLM gets |
|---|---|
| A. LLM alone | Goal and rule list; Lean feedback |
| B. + PDDL | A, plus the legal-move list at each step |
| ~~C. + hand-written KG~~ | Dropped 2026-11-25: there is no hand-written graph |
| D. + PDDL + KG (extracted) | B, plus the LLM-built graph |
| E. Oracle | B, plus the right strategy given up front |
| W. Whole proof first | Goal and rule list. The LLM writes the **entire** deduction (numbered lines: sequent, rule, premise lines, extra formulas) in one answer. Then the gates check it **line by line, in order**, and record for each line: accepted, or which side condition failed. No legal-move list and no feedback during writing |

**Why W (added 2026-11-25, author's decision):** it compares *planning the whole proof* with *building it move by move with legal moves* (B). W is close to ProofGrid's one-shot setup, so W vs. B measures what the per-step legal-move layer adds over the standard approach. W uses the same gates and the same Lean export; the only new code is a replay function that feeds the lines to the gates in order. Metrics for W: proofs fully accepted, **first failing line** (position and type), and how many lines are valid after the first error. *Optional later:* W+R, which sends the first gate error back for one repair round. 'Repair, Retry' (arXiv 2610.22698) found that feedback like this often doesn't beat resampling, so treat it as secondary.

Models: one small local model and one strong API model. Use at least 3 seeds and a fixed step budget.

Metrics:
- Proofs Lean accepts (%)
- Steps per proof
- Rejected steps
- Out-of-candidate-set proposals
- A **failure taxonomy**, the main contribution: wrong rule shape, assumption-order errors with →I, failing to find Contr, and so on

Use paired McNemar tests between conditions, as in the calculus study.

## Design update (2026-11-12): the Proof World

The author's revised architecture reuses the agent-sandbox text-adventure engine. The plan is `docs/superpowers/plans/2026-11-12-proof-world.md`.

- **Rooms** are assumption sequences `S`. **Items** in a room are proved lines `S ⊢ φ`. The starting room holds the problem's assumptions, and `take` is the Assume rule.
- **Gates** are Python functions, one per rule, called from each engine `Action`'s precondition check. **These replace the PDDL file.** The engine's actions already work like classical-planning action schemas. A PDDL export stays optional, used only for shortest-proof search.
- **Search direction is now forward** (from the assumptions toward the goal), not backward as in §4.1. Free formulas for ∨I and Expand are limited to the candidate set, as in §4.2.
- **The knowledge graph** reaches the player through the engine's `read_plan` and `query_knowledge` tools.
- **Lean** verifies the exported trace of accepted moves. Any trace the Python gates accept but Lean rejects counts as a gate bug.
